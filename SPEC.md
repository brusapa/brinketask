# V1 specification — tasks and reminders app

Status: approved. Date: 2026-10-07.
Project name: `brinketask`.

This document and `api/openapi.yaml` are the source of truth; `DESIGN.md` is the visual reference for the web client. If code and specification disagree, one of them is fixed in the same change; the discrepancy is never left in place.

## 1. Goal and scope

Self-hosted tasks and reminders application, multi-user at low volume, with an API designed so that a native Android client (V2) and offline work (future) can be added without breaking the contract.

### In V1

- Tasks with checklist, lists, tags, priority, manual ordering and due date.
- Recurrence (RRULE subset).
- Multiple reminders per task, delivered through Web Push.
- Web client (PWA), always online.
- OIDC authentication against Pocket ID.
- Incremental sync endpoint (already used by the web client to refresh; it is the basis for offline).

### Out of V1 (do not implement, but do not prevent)

| Topic | Provision in V1 |
|---|---|
| Collaboration (sharing lists, assigning, commenting) | `list_members` table and membership-based authorization from day one |
| Offline work | Client-generated IDs, idempotent operations, partial `PATCH`, tombstones, change cursor |
| Email reminders (SMTP) | Notification channel interface |
| Native Android (V2), iOS (long term) | `bearerAuth` scheme declared in OpenAPI; extensible push channel |
| UI language selection (Spanish, V2) | All UI and notification texts externalized from day one; V1 ships English only. V2 adds a `locale` user setting (additive API change) |
| Keyboard shortcuts (V2) | Nothing |
| View of completed tasks older than the current day | Done tasks and completion records are kept and exposed by the API |
| Data import | Nothing |
| Calendar, kanban, pomodoro, habits | Nothing; out of product scope |

## 2. Architecture

- **Backend**: Go. A single binary that serves the API, runs the reminder scheduler and serves the web client's static files (embedded).
- **Database**: PostgreSQL. It also acts as the job queue; there is no Redis or broker.
- **Web**: React + TypeScript, SPA installable as a PWA, with a service worker for Web Push.
- **Deployment**: one container image for the application plus PostgreSQL. TLS is terminated by the external reverse proxy. HTTPS is mandatory: without it neither the service worker nor Web Push work.
- **Same origin**: API and web client are served from the same origin. This simplifies cookies, CSRF and the service worker.

## 3. Design decisions

Each decision has an identifier so it can be cited in commits and reviews.

| ID | Decision | Rationale |
|---|---|---|
| D-01 | OpenAPI first; server and clients are generated from the file | Single contract for web and Android |
| D-02 | OpenAPI 3.0.3, not 3.1 | Safe compatibility with Go generators. Revisit if the chosen generator supports 3.1 reliably |
| D-03 | UUID IDs generated by the client (v7 recommended) | Create offline and retry without duplicating |
| D-04 | Idempotent creation `POST`: repeating it with the same `id` returns the existing resource | Safe retries |
| D-05 | `PATCH` with JSON Merge Patch (RFC 7396); only the fields sent are touched | Per-field conflict resolution: the last write to reach the server wins |
| D-06 | Soft delete (`deleted_at`) on every syncable resource | Trash and sync tombstones through the same mechanism |
| D-07 | Global sync counter (`seq`) assigned under a lock on every write | Change cursor with no gaps from concurrent transactions, and valid for shared lists in V2. It serializes writes; acceptable at low volume |
| D-08 | Subtasks are simple checklist items (no date, reminders or nesting) | Product decision |
| D-09 | Recurring task = a single row whose date advances on completion, plus a completion log | Avoids one row per occurrence and duplicates |
| D-10 | Completing requires `occurrence_due_date`; if it does not match the current due date, the operation does nothing | Completing the same occurrence from two devices does not advance twice |
| D-11 | Recurrence stored as RRULE text; the expansion engine is our own and covers only the subset | The end-of-month adjustment departs from RFC 5545, so a standard library would give a different result |
| D-12 | Manual ordering with fractional indexes (sortable strings) generated by the client | Reordering touches a single row |
| D-13 | OIDC authentication with the backend as a confidential client; own session in a cookie | The web client never handles tokens |
| D-14 | User identified by (`iss`, `sub`); never by email | Email can change at the provider |
| D-15 | Notification channels behind an interface; V1 implements only Web Push | SMTP and Android push are added as new channels |
| D-16 | Polling scheduler on PostgreSQL (`FOR UPDATE SKIP LOCKED`) | No additional dependencies |
| D-17 | Domain code does not read the clock directly; it receives an injected clock | Deterministic tests for recurrence and reminders |
| D-18 | A single image (Go binary with the web client embedded) | Same origin and minimal deployment |

## 4. Data model

Conventions:

- Every syncable table carries: `id uuid`, `version int` (incremented on every write), `seq bigint` (see D-07), `created_at`, `updated_at`, `deleted_at` (null while alive).
- Timestamps in UTC (`timestamptz`). Calendar dates as `date`. Local times as `time` without zone.

### users

| Field | Type | Notes |
|---|---|---|
| id | uuid | Generated by the server |
| oidc_issuer, oidc_subject | text | Unique together (D-14) |
| email, display_name | text | Copied from the claims on every login; informational |
| timezone | text | IANA zone. Defaults to `Europe/Madrid`; the client updates it |
| all_day_reminder_time | time | Reminder time for tasks without a time. Defaults to `09:00` |
| created_at, updated_at | timestamptz | |

### lists (syncable)

| Field | Type | Notes |
|---|---|---|
| owner_id | uuid | Creating user |
| name | text | 1–200 characters |
| color | text, nullable | `#RRGGBB` |
| position | text | Fractional index |
| is_inbox | bool | Exactly one per user; created at sign-up; cannot be deleted or renamed |

### list_members

`(list_id, user_id, role)` with `role` in `owner | editor | viewer`. In V1 only the `owner` row exists, created together with the list. **Every authorization query goes through this table**, not through `lists.owner_id`.

### tasks (syncable)

| Field | Type | Notes |
|---|---|---|
| list_id | uuid | |
| title | text | 1–500 characters |
| description | text | Markdown, up to 20,000 characters |
| status | enum | `open`, `done`, `dropped` |
| priority | smallint | 0 none, 1 low, 2 medium, 3 high |
| position | text | Fractional index within the list |
| due_date | date, nullable | |
| due_time | time, nullable | Requires `due_date` |
| due_tz | text, nullable | IANA zone. Requires `due_time`. Null = floating time |
| rrule | text, nullable | Requires `due_date`. See section 5 |
| repeat_from | enum | `due` or `completion` |
| recurrence_done_count | int | Occurrences completed or skipped; used for `COUNT` |
| completed_at | timestamptz, nullable | Only with `status = done` |
| tag_ids | uuid[] | Tags sync as a field of the task |

Due types:

1. **No date**: `due_date` null.
2. **All-day**: `due_date` only.
3. **Floating time**: `due_date` + `due_time`, no `due_tz`. Interpreted in the user's current zone ("9:00 wherever I am").
4. **Fixed time**: all three fields. An absolute instant.

### checklist_items (syncable)

`task_id`, `title` (1–500), `is_done`, `position`.

### tags (syncable)

`owner_id`, `name` (1–50, unique per user, case-insensitive), `color`.

### reminders (syncable)

| Field | Type | Notes |
|---|---|---|
| task_id | uuid | |
| kind | enum | `relative`, `absolute`, `snooze` |
| offset_minutes | int, nullable | `relative` only. Minutes before the due instant, 0–40320 |
| at | timestamptz, nullable | `absolute` and `snooze` only |
| next_fire_at | timestamptz, nullable | Computed by the server; null = nothing pending |
| last_fired_at | timestamptz, nullable | |

At most 5 live reminders per task (`snooze` reminders do not count).

### task_completions

`id` (from the client), `task_id`, `kind` (`completed | skipped`), `occurrence_due_date`, `completed_at`, and the previous state needed to undo: `prev_due_date`, `prev_due_time`, `prev_recurrence_done_count`, `prev_status`.

### push_subscriptions

`id`, `user_id`, `channel` (V1: `webpush`), `endpoint` (unique), `p256dh`, `auth`, `label`, `created_at`, `last_success_at`, `disabled_at`.

### notification_deliveries

`id`, `reminder_id`, `fire_at`, `subscription_id`, `status` (`pending | sent | failed | skipped`), `attempts`, `sent_at`, `error`. Unique on (`reminder_id`, `fire_at`, `subscription_id`) so nothing is sent twice.

### sessions

`id_hash` (hash of the session identifier; the clear value lives only in the cookie), `user_id`, `created_at`, `last_seen_at`, `expires_at`.

### sync_state

A single row holding the global `seq` counter (D-07).

## 5. Recurrence

### Supported subset

| RRULE part | Accepted values |
|---|---|
| `FREQ` | `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY` |
| `INTERVAL` | 1–999 |
| `BYDAY` | Only with `WEEKLY`; days without ordinal prefix (`MO,WE`) |
| `BYMONTHDAY` | Only with `MONTHLY`; a single value 1–31 or `-1` (last day) |
| `COUNT` or `UNTIL` | Optional and mutually exclusive |

Any other part is rejected with 422. The start of the series (`DTSTART`) is the task's current due date; it is not stored in the string.

### Rules

- **R-1 End-of-month adjustment**: if the requested day does not exist in the month (31 in April, 29 February in a non-leap year), the last day of the month is used. *This departs from RFC 5545, which skips those months.* The "desired" day is preserved: a task on the 31st returns to the 31st in months that have it.
- **R-2 `due` mode**: the next date is the first occurrence of the series after the current due date and not earlier than today (user's zone). Overdue intermediate occurrences are discarded.
- **R-3 `completion` mode**: next date = completion date (user's zone) + `INTERVAL` × `FREQ`. In this mode `BYDAY` and `BYMONTHDAY` are not accepted (422). This is not standard RRULE; that is why the `repeat_from` field exists.
- **R-4** The time (`due_time`, `due_tz`) is preserved across occurrences. With a fixed time, the local time is kept across daylight saving changes.
- **R-5 End of the series**: if the next date is past `UNTIL`, or `recurrence_done_count` reaches `COUNT`, the task becomes `done` for good.
- **R-6 Skip**: same as completing, but the record is `skipped`. It counts towards `COUNT`.
- **R-7** When a task advances, its checklist items go back to `is_done = false`.
- **R-8** On advancing or completing, `absolute` and `snooze` reminders are deleted (tombstone); `relative` ones are recomputed.

### Complete and undo

- `POST /tasks/{id}/complete` with `completion_id` (from the client) and `occurrence_due_date`.
  - `completion_id` already exists → idempotent response, no changes.
  - `occurrence_due_date` differs from the current `due_date` → not applied (`applied: false`) and the current state is returned (D-10).
  - Non-recurring task → `status = done`.
  - Recurring task → the next date is computed (R-2 to R-5).
- `POST /tasks/{id}/uncomplete` with `completion_id`: restores the saved previous state. Only the latest record of the task can be undone (409 otherwise). If the record does not exist, it does nothing. Reminders deleted by R-8 are not restored.
- `status = dropped` is set with `PATCH`; `done` only through `complete`.

## 6. Reminders

### Computing the fire instant

| Due type | `relative` reminder |
|---|---|
| Fixed time | Due instant − `offset_minutes` |
| Floating time | Due in `users.timezone` − `offset_minutes` |
| All-day | `due_date` at `users.all_day_reminder_time` in `users.timezone` − `offset_minutes` (0 = that day; 1440 = the day before) |
| No date | `relative` not allowed (422) |

`absolute` and `snooze` use `at` directly.

`next_fire_at` is recomputed when any of these change: the reminder, the task's due date or status, the user's zone or default time, or when a recurrence advances. It is null if the task is not `open`, is deleted, or the computed instant is already in the past at computation time.

### Scheduler

- Polls every 15 s (configurable) for reminders with `next_fire_at <= now()`, using `FOR UPDATE SKIP LOCKED`.
- For each one it creates a delivery per active subscription of the user, sets `next_fire_at` to null and sets `last_fired_at`.
- If the delay exceeds `REMINDER_MAX_LATENESS` (default 12 h, e.g. after an outage), the delivery is marked `skipped` and nothing is sent.
- Punctuality target: reminder handed to the push service less than 60 s late.
- Retries with exponential backoff, at most 5. A 404 or 410 from the push service disables the subscription.

### Notification

- Content: task title, list name, due date. The payload is encrypted (Web Push standard with VAPID keys).
- Actions: **Complete** and **Snooze** (10 min, 1 h, tomorrow at the default time). The service worker performs them against the API using the session cookie; if the session has expired, it opens the app.
- Snooze = `POST /tasks/{id}/snooze`, which creates a `snooze` reminder.
- Notification texts (action labels, date formatting) are externalized like the rest of the UI (section 9).

### Limitations accepted in V1

- Completing a task on one device does not dismiss the notification already shown on another.
- On iOS, Web Push only works if the web app is installed on the home screen.
- Notification action buttons are not available in every browser; where they are missing, tapping the notification opens the task.

## 7. Authentication and authorization

- Flow: authorization code with PKCE (S256), `state` and `nonce`. Configuration through discovery (`/.well-known/openid-configuration`). Scopes: `openid profile email`.
- Routes (outside `/api/v1`, they are browser redirects): `GET /auth/login`, `GET /auth/callback`, `POST /auth/logout`.
- Automatic sign-up on first login: the user and their inbox are created.
- Who may log in is decided in Pocket ID (allowed groups of the OIDC client). The app has no registration and no passwords.
- Session: random opaque identifier in a `HttpOnly; Secure; SameSite=Lax` cookie; only its hash is stored in the database. Sliding expiry of 7 days and absolute expiry of 30 (configurable).
  - *Accepted trade-off*: a user revoked in Pocket ID keeps access until their session expires. Mitigation: delete their rows in `sessions`.
- CSRF: cookie-authenticated state-changing requests must be same-origin (`Origin` / `Sec-Fetch-Site` check); otherwise 403.
- Authorization: every access to a list, task, item or reminder is validated against `list_members`. A resource belonging to someone else answers 404, not 403.
- V2: the API will accept `Authorization: Bearer`. The concrete mechanism (validating Pocket ID tokens or issuing our own) is decided then; user resolution must live in a single middleware.

## 8. API

Full detail in `api/openapi.yaml`. Conventions:

- Base `/api/v1`. JSON. Timestamps RFC 3339 in UTC; dates `YYYY-MM-DD`; times `HH:MM`.
- Errors in `application/problem+json` format (RFC 9457) with a stable `code` field for the client.
- Pagination through an opaque cursor (`cursor`, `limit`).
- Delete answers 204 and is a soft delete. Restoring is possible for 30 days; the row is physically purged after 90.
- Deleting a list deletes its tasks in the same operation; restoring it restores the tasks deleted with it.

### Sync

`GET /sync/changes?cursor=…` returns the resources whose `seq` is greater than the cursor, tombstones included, and a `next_cursor`. Without a cursor it returns the full live state. A cursor older than tombstone retention (90 days) answers 410 and forces a resync from scratch.

In V1 the web client uses it to refresh when it regains focus. There is no real-time channel in V1.

### Views

"Today" (includes overdue) and "Next 7 days" are computed by the client with the `due_from` / `due_to` filters in the user's zone. There are no dedicated endpoints.

### Completed section

The section is fed by completion records, not by tasks with `status = done`, so that a completed occurrence of a recurring task shows up even though the task itself stays open (D-09).

- `GET /completions` returns records of kind `completed` (never `skipped`) with a summary of their task, filtered by completion time and by the same scope as the view: `list_id`, `tag_id`, or `due_from` / `due_to` applied to `occurrence_due_date`.
- The client asks for the current calendar day in the user's zone (`completed_from` / `completed_to`). The server applies no day logic of its own.
- Records whose task is deleted are omitted. The title shown is the task's current title.
- Unchecking an entry calls `uncomplete` with its `completion_id`. Only the latest record of a task can be undone, so an older entry of the same task is shown without an active checkbox.

### Search

`q` parameter over title and description, case- and accent-insensitive. Implementation is free (e.g. `pg_trgm`).

## 9. Web client

- Layout: three panes. Sidebar (Inbox, Today, Next 7 days, lists, tags, Trash, Settings), task list with a quick-add field on top, and a task detail panel on the right. The detail panel exists only while a task is selected and disappears when none is.
- Narrow screens: single column, sidebar as a drawer, task detail full screen. The mobile web layout is a first-class target in V1: the installed PWA is the phone client until the Android app exists.
- Density: compact, with little white space. Rows of about 36 px on pointer devices; on touch devices every target is at least 44 px.
- Theme: light and dark, following the system preference; light when the system states none. No manual switch in V1.
- Completed tasks: a collapsed "Completed" section at the end of each list and view, shown greyed out and struck through. It lists what was completed during the current calendar day in the user's zone and empties at local midnight (section 8, "Completed section").
- There is no view of older completed tasks: after that day they are no longer visible anywhere in the UI, search included. They stay stored and reachable through the API.
- No keyboard shortcuts in V1. Standard keyboard operability (Tab order, Enter to submit, Escape to close the panel) is still required.
- Components come from an established, accessible component library, chosen in phase 3; no bespoke widget set.
- Visual reference: `DESIGN.md` (layout, metrics and colour tokens of the approved mockups).
- Screens: inbox, list, Today, Next 7 days, tag, search, trash, settings (time zone, default reminder time, devices with notifications).
- Task detail: every field, checklist, reminders, recurrence editor limited to the subset.
- Undo: temporary toast after deleting or completing, which calls restore or `uncomplete`.
- Drag to reorder; move tasks between lists.
- The client detects the browser's time zone and offers to update the profile if it differs.
- Types and HTTP client generated from `api/openapi.yaml`; never written by hand.
- UI language: English by default and the only language in V1. Every user-facing string goes through an i18n layer with message catalogs from day one; no hard-coded literals in components. Dates and times are formatted with the platform's locale-aware APIs. Spanish as a selectable language is V2.

## 10. Non-functional requirements

- **Configuration** through environment variables; every secret accepts a `_FILE` variant (path to a file). Minimum: `DATABASE_URL`, `PUBLIC_URL`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`.
- **Migrations** embedded in the binary, applied at startup, forward-only.
- **Observability**: structured JSON logs with no personal data or task content; `GET /healthz`; Prometheus metrics at `GET /metrics` (separate internal port).
- **Security**: strict CSP headers, request size limits, per-session rate limit, version-pinned dependencies, non-root container with a read-only file system.
- **Backups**: all state lives in PostgreSQL; document dump and restore.
- **Performance**: no formal target. Reference: 50 users, 10,000 tasks per user, read responses under 200 ms.

## 11. Testing

- **Recurrence**: table-driven tests of the engine. Mandatory cases: end of month (R-1), leap years, `Europe/Madrid` clock changes (last Sunday of March and of October), `COUNT`, `UNTIL`, heavily overdue task (R-2), `completion` mode.
- **Reminders**: `next_fire_at` computation for the four due types, user zone change, maximum lateness, no duplicate deliveries.
- **Idempotency**: repeating every creation `POST` and every action (`complete`, `skip`, `uncomplete`, `snooze`) leaves the same state.
- **Completed section**: `GET /completions` returns a completed occurrence of a recurring task, omits skipped records and deleted tasks, and respects the time and scope filters.
- **Sync**: concurrent writes leave no change outside the cursor; tombstones appear; expired cursor → 410.
- **Authorization**: a user cannot read or modify another user's resources (404).
- **Contract**: real responses validate against `api/openapi.yaml`.
- **Integration** against a real PostgreSQL, not a mock.
- **End-to-end**, minimal, in a browser: log in (test OIDC provider), create, complete, undo, receive a reminder.
